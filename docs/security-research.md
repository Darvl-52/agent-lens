# Какие дыры ловит часть security и почему

Заметка к `hooks/security/`: откуда взят список классов атак и что можно проверить без модели.
Источники проверены 2026-10-31. Это короткая выжимка из первоисточников, а не полный обзор: разбор
каждого класса с примерами кода не делался.

## Что говорят первоисточники

**[OWASP Top 10:2025](https://top10.owasp.org/2025)**: A01 Broken Access Control, A02 Security
Misconfiguration, A03 Software Supply Chain Failures, A04 Cryptographic Failures, A05 Injection, A06
Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security
Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions.

**[CWE Top 25, 2025](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html)**. Первые четыре
места: XSS (CWE-79), SQL-инъекция (CWE-89), CSRF (CWE-352), отсутствие авторизации (CWE-862). Для
веб-кода важны также path traversal (CWE-22), OS command injection (CWE-78), code injection (CWE-94),
небезопасная загрузка файлов (CWE-434), десериализация (CWE-502), раскрытие данных (CWE-200), нет
аутентификации у критичной функции (CWE-306), SSRF (CWE-918), авторизация по ключу от клиента, то есть
IDOR (CWE-639), и нет лимитов на ресурсы (CWE-770). Ошибки памяти из этого списка плагин не ищет.

**[Veracode, GenAI Code Security Report, 2025](https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/)**.
Больше 100 моделей, 80 задач: уязвимость появилась в 45% случаев. Хуже всего с XSS (CWE-80, провал в
86%) и log injection (CWE-117, провал в 88%). Поэтому эти два класса стоят первыми в списке агента,
хотя log injection нет ни в первой десятке OWASP, ни в CWE Top 25.

**[Правила gitleaks](https://raw.githubusercontent.com/gitleaks/gitleaks/master/config/gitleaks.toml)**:
форматы токенов провайдеров. Правила прочитаны через сводку инструмента, регулярки в `scan.ts` написаны
по ним, но не скопированы один в один: они шире или уже там, где это указано ниже.

## Что проверяется без модели, а что нет

| Проверка | Как | Что происходит |
| --- | --- | --- |
| Секрет известного формата | Регулярка по `scan.ts` | Отказ до записи |
| Дыра, видимая в самой правке | Модель (`haiku`) до записи | Отказ до записи; на третью попытку в файле за ход правка проходит и попадает в журнал |
| Опасный вызов (`innerHTML`, SQL из строки, `eval`, ...) | Регулярка по добавленным строкам | Подсказка модели и агенту; заметка Claude, только если модель не ответила или проверка выключена |
| Авторизация, IDOR, CSRF, SSRF, цепочки данных через файлы | Только чтением кода | Агент после хода |

Регулярка не видит, откуда пришли данные, поэтому опасный вызов не повод для отказа. Авторизацию по
диффу не проверить вовсе: дыра в том, чего в коде нет. Этим и заняты разные слои.

Отличия от gitleaks, сделанные сознательно:

- Ключи Stripe: отказ только для `live`. Тестовые ключи не считаются утечкой.
- OpenAI и Anthropic: шаблоны шире, чем у gitleaks, потому что форматы менялись. Цена: возможны ложные
  срабатывания на длинных строках с префиксом `sk-`. Исключением служит `/security allow`.
- Приватный ключ: как и у gitleaks, нужно тело ключа. Код, который лишь ищет заголовок PEM, не считается
  секретом.

## Что не подтверждено

- Страница OWASP не называет версию ни финальной, ни кандидатом в релиз; сторонние публикации называют
  список финальным.
- Более свежие цифры Veracode за 2026 год (XSS около 15% успеха, log injection около 13%) найдены только
  во вторичных обзорах. Здесь они не используются.
- На реальных проектах доля ложных срабатываний сканера не измерена. Тесты в `tests/security.test.tsx`
  проверяют только выбранные примеры.
